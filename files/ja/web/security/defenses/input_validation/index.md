入力検証とは、ウェブサイトが受け付けるあらゆる入力が、想定しているものかどうかを確認する方法です。

ウェブサイトでほとんどあらゆる種類の対話やカスタマイズを提供するためには、何らかの入力を受け付ける必要があります。これは通常、ウェブブラウザー経由でユーザーから入力され、他のアプリケーションからの場合もあります。

ユーザーは通常、サイトのフロントエンドにある {{htmlelement("form")}} 要素内の {{htmlelement("input")}} 要素に情報を入力し、そのデータは通常、{{httpmethod("POST")}} リクエストの本文、または {{httpmethod("GET")}} リクエストに追加された URL 引数としてサーバーに送信されます。ただし、入力はクッキー値や追加の HTTP ヘッダーなど、他の方法でサーバーに届く場合もあります。

ユーザーが提供した入力が、サイトが想定する形式または内容を持っていない場合（例えば、無効な形式のメールアドレスが入力された場合）、サイトが誤動作することがあります。このような問題をできるだけ早く検出することで、ユーザーの使い勝手が向上します。

しかし、ユーザーの単なるミスとは別に、予想外の入力を提供されると、悪意ある行為者がクロスサイトスクリプティング (XSS)、SQL インジェクション、コマンドインジェクションなど、さまざまなセキュリティ攻撃を試みることができてしまいます。このような状況では、攻撃者が攻撃を可能にする何らかの入力を意図的に作成し、アプリケーションに渡します。攻撃者はウェブサイトのフロントエンドを完全に迂回し、悪意ある入力を HTTP リクエストで直接提供する可能性があります。入力検証は通常、これらのセキュリティ上の脅威に対する完全な解決策ではありませんが、重要な第一の防御線です。

## 検証ガイドライン

### 許可リストとして検証を実装する

アプリケーションでは、特定の検査を、許可される値（「許可リスト」）または拒否される値（「拒否リスト」）で指定することにより実装できます。

例えば、数値入力が 0 以上 10 以下であることを検査したい場合、入力がこの範囲内かどうかを確認し、それ以外をすべて拒否する許可リストとして実装できます。

```js
function checkRange(input) {
  if (input >= 0 && input <= 10) {
    return true;
  }
  return false;
}
```

代わりに、拒否リストとして、入力が範囲外かどうかを検査し、それ以外をすべて許可するように実装できます。

```js
function checkRange(input) {
  if (input < 0 || input > 10) {
    return false;
  }
  return true;
}
```

検査を許可リストとして実装する方が、通常は信頼性が高く、作成者が想定していなかった値をデフォルトで拒否できます。無効な入力が攻撃者によって意図的に作成されている場合は特にそうです。検査を回避し、デフォルトの「許可」条件に通過する入力を攻撃者が提供する方が容易だからです。

### 構文検証と意味検証

入力検証には 2 種類あります。

- 「構文検証」は、入力が正しい形式かどうかを検査します。例えば、アプリケーションが数値を受け取ることを想定している場合、その入力が数値であるかを確認します。
- 「意味検証」は、入力の内容が想定された範囲内かどうかを検査します。例えば、特定の範囲内にあるべき数値や、許可された値の集合の中から正確に一致する文字列値などを確認します。

アプリケーションでは、通常、選択したプログラミング言語の型検査機能を使用して構文検証を実装します。

意味検証を実装するには、範囲検査、許可された値の集合に対する値の検査、複雑な場合には正規表現など、さまざまな方法を使用できます。

正規表現は正しく記述することが難しく、一部の式ではアプリケーションが[サービス拒否攻撃](https://community.owasp.org/attacks/Regular_expression_Denial_of_Service_-_ReDoS)に対して脆弱になる可能性があります。このため、通常は評判のよいサードパーティーの検証ライブラリーを使用する方がよいでしょう。[validator.js](https://github.com/validatorjs/validator.js) は人気のある選択肢の 1 つです。

### 検証のタイミング

アプリケーションは、入力直後にできるだけ早く検証すべきです。そうすることで、ユーザーに問題をすぐにフィードバックし、修正する機会を与えることができます。一般的には、ウェブサイトのフロントエンドコードでクライアント側から入力を検証する必要があります。

ただし、攻撃者はフロントエンドコードを改変または完全に迂回する可能性があるため、セキュリティ上の問題を検出するためにフロントエンドでの検証だけに頼ってはいけません。そのため、入力を処理する前にサーバーでも検証する必要があります。

## クライアント側の検証

HTML の {{htmlelement("input")}} 要素は、ユーザーが提供する入力に有効な値を定義するための多数の属性に対応しています。主なものは次の通りです。

- [`type`](/ja/docs/Web/HTML/Reference/Elements/input#input_の型) は、想定される入力の型を定義し、その型に基づいて検証を実行します。例えば、`type` が [`email`](/ja/docs/Web/HTML/Reference/Elements/input/email) の場合、ブラウザーは入力が構文的に有効なメールアドレスかを自動的に確認します。

- [`minLength`](/ja/docs/Web/HTML/Reference/Attributes/minlength) と [`maxLength`](/ja/docs/Web/HTML/Reference/Attributes/maxlength) は、テキスト入力で許可される最小文字数と最大文字数を定義します。

- [`min`](/ja/docs/Web/HTML/Reference/Attributes/min) と [`max`](/ja/docs/Web/HTML/Reference/Attributes/max) は、数値で許可される最小値と最大値を定義します。

- [`step`](/ja/docs/Web/HTML/Reference/Attributes/step) は、数値入力で許可される値の間隔を定義します。

- [`pattern`](/ja/docs/Web/HTML/Reference/Attributes/pattern) は、テキスト入力が一致する必要がある正規表現を定義します。

要素の {{domxref("HTMLElement/change_event", "change")}} イベントにイベントハンドラーを追加することで、JavaScript に独自の有効性検査を定義できます。イベントハンドラー内で独自の有効性検査を実行し、要素の {{domxref("HTMLInputElement/setCustomValidity", "setCustomValidity()")}} メソッドを呼び出してその有効性を設定できます。

入力の検証に失敗した場合、ブラウザーはフォームを送信せず、ユーザーにエラーメッセージを表示します。

[HTML フォーム検証の使用](/ja/docs/Web/HTML/Guides/Constraint_validation)で詳細を確認できます。

## サーバー側の検証

サーバー側では、可能であれば、選択したフレームワークが提供する検証関数（Django の[バリデーター](https://docs.djangoproject.com/en/stable/ref/validators/)など）をアプリケーションで使用すべきです。

サイトのフロントエンドを操作しているユーザーが発生させることのない検証失敗には、特に注意を払うことが重要です。例えば、フォームの HTML で提供されていなかったオプションが含まれる {{htmlelement("select")}} 要素は、このような失敗は攻撃者が意図的に不正な入力を作成していることを示す強い兆候です。

入力が JSON として表現される場合、[JSON Schema](https://json-schema.org/) を使用して有効性を定義できます。[OpenAPI](https://swagger.io/) を使用して指定される API にも適用できます。データベースを使用する場合は、データベーススキーマを定義し、そのスキーマに対して入力を検証することもできます。

## ファイルアップロード

サイトでファイルアップロードを許可する場合、さまざまな追加の脅威を考慮する必要があります。攻撃者は次のような行為を行う可能性があります。

- 処理ソフトウェアのバグを悪用する悪意あるファイルをアップロードする。
- サービス拒否攻撃の一環として、非常に大きなファイルをアップロードする。
- 好ましくないコンテンツや違法なコンテンツをアップロードする。
- ファイル処理コードを混乱させて、独自のサイトのファイルを上書きさせる。
- XSS などの悪用に利用できるファイルをアップロードし、他のユーザーにダウンロードさせて実行させる。

これらの脅威を軽減するには、次のベストプラクティスが一般的に使用されます。

- 認証済みユーザーだけがファイルをアップロードできるようにする。

- ファイル名もユーザー入力であるため、検証する必要があります。可能であれば、保存するファイルには独自の名前を生成します。ユーザーが指定した名前を使用しなければならない場合は、ユーザーが選択できる文字を厳しく制限し、その文字に対して名前を検証します。

- 対応が必要なファイルタイプを特定し、ファイル拡張子に基づいて、それらのタイプだけを許可します。HTML や JavaScript などのウェブで実行可能なファイルタイプには特に注意が必要です。ファイル拡張子の検査にはユーザーが指定したファイル名の処理が必要になるため、まずファイル名を検証してください。

- アップロードできるファイルのサイズを制限する。

- ユーザーが好ましくないコンテンツや違法なコンテンツを報告できるようにし、それらを削除する手順を用意する。

- 可能であれば、ファイルを別のホストに保存します。これが不可能な場合は、ウェブサイトのルート外に保存します。これにより、悪意あるアップロードが XSS などの攻撃で他のユーザーに提供されるリスクが低下します。

詳細については、OWASP の [ファイルアップロード早見表](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)<sup>(英語)</sup> を参照してください。

## 入力検証とセキュリティ

悪意ある入力をサイトが受け入れてしまうと、サイトが意図せずその内容をコードまたはコマンドとして実行する攻撃経路となります。これには次のものが含まれます。

- クロスサイトスクリプティング (XSS) 攻撃: ブラウザーが悪意あるコードをウェブサイトの一部であるかのように実行します。

- SQL インジェクション攻撃: サーバーが悪意ある SQL クエリーをデータベース上で実行します。

- コマンドインジェクション攻撃: サイトがホストのオペレーティングシステム上で悪意あるコマンドを実行します。

ここで説明した一般的な入力検証は、このような攻撃に対する有用な第一の防御線ですが、完全な防御策でも、主な防御策でもありません。これは、入力が使用される具体的なコンテキストが分からない場合、これらの攻撃から保護することが非常に難しいためです。

代わりに、アプリケーションはこれらの攻撃に特化した防御策を使用すべきです。

- [クロスサイトスクリプティング (XSS) の防御](/ja/docs/Web/Security/Attacks/XSS)。

- [SQL インジェクション防止早見表](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)<sup>(英語)</sup>。

- [コマンドインジェクション防御早見表](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)<sup>(英語)</sup>。

このガイドでは、書いたコードそのものに直接関係するものではなく、プロジェクトの開発、ビルド、出荷、更新をどのように行うかに関係するセキュリティの方法を説明します。

これらの多くは、攻撃者がウェブサイトの開発工程を改変し、悪意あるコードや脆弱なコードを導入する[サプライチェーン攻撃](/ja/docs/Web/Security/Attacks/Supply_chain_attacks)に対する防御策です。サプライチェーン攻撃への防御策は、通常、開発工程を保護する方法です。

このガイドは、以下の節に分けています。

- 開発環境の保護: 独自のコードの開発や更新の方法に関する慣行が含まれます。

- 依存関係の管理: ほとんどすべてのソフトウェアプロジェクトは、第三者が作成したパッケージに依存しています。この節では、それらを使用する際のリスクを低減するために従うべき慣行を説明します。

- 監視と対応: プロジェクトのセキュリティ上の問題を発見し、それに対応するための慣行を説明します。

- 安全なバックアップ。

## 開発環境の保護

この節では、攻撃者によるプロジェクトのコードの侵害を防ぐために実行できる手順を説明します。

### プロジェクトメンテナーに強固な認証を要求する

メンテナーのアカウントの制御権を取得されると、攻撃者は悪意あるコードを導入したり、製品の悪意ある更新を出荷したりできます。

そのため、プロジェクトではメンテナーのアカウントに強固な認証方法を使用する必要があります。

- 可能であれば、メンテナーの認証に[パスキー](/ja/docs/Web/Security/Authentication/Passkeys)を使用してください。

- それが不可能な場合は、パスワードと[時間ベースのワンタイムパスワード (TOTP)](/ja/docs/Web/Security/Authentication/OTP#totp)を組み合わせた {{glossary("multi-factor authentication", "多要素認証 (MFA)")}} を使用してください。

攻撃者はメンテナーのアカウントの制御権を取得するために、しばしば[フィッシング](/ja/docs/Web/Security/Attacks/Phishing)を使用します。MFA を使用するとフィッシングは困難になりますが、[ほとんどの形式の MFA はフィッシングを防止できません](/ja/docs/Web/Security/Attacks/Phishing#多要素認証)。パスキーはフィッシング攻撃に対する最も強固な防御策です。

### プロジェクトメンテナーにロールベースのアクセス制御を実装する

プロジェクトは、メンテナーが実行する作業に必要な権限だけを、そのメンテナーに付与すべきです。例えば、プロジェクトのセキュリティ設定を変更できるメンテナーや、新しいリリースを作成できるメンテナーを、一部に限定できます。これにより、メンテナーのアカウントが侵害された場合に攻撃者が与えられる被害を抑えられます。

### 使用するツールを評価する

[サードパーティーの直接依存関係](#サードパーティーの依存関係の管理)とは別に、プロジェクトでは通常、ソフトウェアの開発、テスト、出荷の工程で多数のサードパーティー製ツールを使用します。これには、例えば次のものが含まれます。

- テキストエディターや IDE
- エディタープラグイン
- ソース管理システム
- ビルド、テスト、デプロイの工程で使用するすべてのツール

攻撃者がこれらのツールを侵害できれば、製品を侵害できる可能性があります。このリスクを低減するには、ツールを使用する前に評価します。オープンソースソフトウェアの依存関係については、[OpenSSF](https://openssf.org/) が公開した[オープンソースソフトウェアを評価するための簡潔なガイド](https://best.openssf.org/Concise-Guide-for-Evaluating-Open-Source-Software)<sup>(英語)</sup>をガイドとして使用できます。

### 設定を保護する

ツール、特にソース管理システムの保護された設定を理解し、適用してください。主要な保護策は次の通りです。

- プルリクエスト (PR) を、マージされる前にコードオーナーによるレビューと明示的な承認を経るようにする。
- プルリクエストを、マージされる前に {{glossary("continuous integration")}} チェックに合格させる。
- コミットに署名を要求する。

GitHub と GitLab に固有のチェックリストを含む、OpenSSF の[ソースコード管理プラットフォーム設定のベストプラクティス](https://best.openssf.org/SCM-BestPractices/)<sup>(英語)</sup>も参照してください。

### 秘密情報を安全に扱う

プロジェクトのメンテナーは通常、パスワードや API キーなど、秘密にしておく必要がある資格情報を使用します。プロジェクトでは、これらが適切に扱われるようにする必要があります。

- 秘密情報は安全に保存してください。
- 秘密情報へのアクセスは制御し、必要なメンテナーだけに限定してください。
- 秘密情報を公共リポジトリーにコミットしてはいけません。ソース管理またはホスティングシステムの一部として、あるいはサードパーティーのサービスとして、リポジトリー内の秘密情報をスキャンするツールを利用できます。

## サードパーティーの依存関係の管理

サードパーティーの依存関係には、コードが使用するライブラリーやフレームワークだけでなく、エディター、IDE、ソース管理システム、パッケージマネージャー、ビルドツールなど、開発工程に関わるすべてのサードパーティー製ツールが含まれます。

サードパーティーの依存関係に関する問題を軽減するため、次の慣行について説明します。

1. 新しい依存関係を評価する
2. 既存の依存関係を更新する
3. ソフトウェア部品表 (SBOM) を維持する

### 新しい依存関係を評価する

新しい依存関係を追加する前に、それがどの程度のセキュリティリスクを表すかを評価すべきです。その依存関係が積極的に保守されていること、問題を修正した実績があること、セキュリティ上の脆弱性を報告して対応するプロセスがあることを確認できる必要があります。

依存関係を追加するリスクが、自分で機能を実装するコストを上回るかどうかを検討すべきです。

[OpenSSF](https://openssf.org/) が公開した[オープンソースソフトウェアを評価するための簡潔なガイド](https://best.openssf.org/Concise-Guide-for-Evaluating-Open-Source-Software)<sup>(英語)</sup>には、新しい依存関係を追加する前に確認すべき質問が記載されています。

### 依存関係を更新する

プロジェクトに依存関係を追加すると、その依存関係の提供元は、通常、新しい機能、バグ修正、セキュリティ修正を含む新しいバージョンを公開します。依存関係を最新の状態に保つ仕組みを実装することで、通常はこれらの更新を利用できます。GitHub の[Dependabot](https://docs.github.com/en/code-security/tutorials/secure-your-dependencies/dependabot-quickstart)<sup>(英語)</sup>などのツールは、依存関係の新しいバージョンを検出し、プロジェクトを更新するプルリクエストを自動的に開始することで、これを支援できます。

ただし、依存関係の更新を積極的に行いすぎると、それ自体にリスクがあります。例えば、信頼できるサードパーティー製パッケージに依存関係を追加するとします。その後、攻撃者がパッケージ開発者のアカウントを制御し、悪意ある更新を公開します。更新をすぐに受け入れると、プロジェクトが侵害されます。

#### ロックファイルを使用する

依存関係の更新を保護するための最初のステップは、依存関係にロックファイルを使用し、ソース管理にコミットし、プロジェクトをビルドする際に使用することです。

[npm](https://www.npmjs.com/) や [Yarn](https://yarnpkg.com/) のようなパッケージマネージャーを使用すると、プロジェクトの依存関係を一覧表示する [package.json](https://docs.npmjs.com/cli/configuring-npm/package-json/)<sup>(英語)</sup>などのファイルを指定できます。その後、指定された依存関係をインストールするコマンドを実行することで、プロジェクトでそれらを使用できます。

ただし、依存関係の一覧だけでは各パッケージの正確なバージョンは決定されません。パッケージ提供元が新しいバージョンを公開すると、プロジェクトのビルド時にそのバージョンが自動的に含まれる可能性があります。依存関係の新しいバージョンが悪意あるものであれば、ユーザーが気づかないうちに、プロジェクトに自動的に含まれる可能性があります。

例えば、package.json に "example-dependency" という名前の依存関係が含まれているとします。

```json
{
  "name": "example-project",
  "version": "1.0.0",
  "dependencies": {
    "example-dependency": "^1.0.2"
  }
}
```

プロジェクトのビルド工程が、提供元が新しいバージョンを公開すると自動的に実行されるとします。ビルド工程では、`npm install` を呼び出すことからビルドを開始します。これにより、バージョン範囲 `"^1.0.2"` に一致する "example-dependency" の最新バージョンが取得されます。

プロジェクトに追加した時点のバージョン `1.0.2` の "example-dependency" は、有用で無害なパッケージです。その後、攻撃者が "example-dependency" の開発者のアカウントを乗っ取り、悪意あるバージョン `1.0.3` を公開します。ビルド工程が実行され、悪意あるパッケージがインストールされ、プロジェクトが侵害されます。

これらの事態はすべて、プロジェクトの直接成果物に変更がないまま、また更新を確認して不審に見えるかどうかを確認する機会もなく発生します。

これに対する解決策は、プロジェクトをビルドする際にロックファイルを使用することです。ロックファイルは、プロジェクトの依存関係がインストールされるたびに自動的に生成され、プロジェクトで使用される直接および間接依存関係の正確なバージョンを一覧表示します。ロックファイルが存在すると、ロックファイルに一覧表示されたもの以外の依存関係バージョンをインストールできなくなります。

つまり、_package.json_ がプロジェクトで "example-dependency" を使用していることを示す場合、_package.lock_ は "example-dependency" を使用する正確なバージョンと、その依存関係のバージョンを示します。

プロジェクトのロックファイルはソース管理にチェックインすべきです。プロジェクトをビルドする際は、ロックファイルを使用してインストールする依存関係のバージョンを制御します。npm では、`npm install` の代わりに [`npm ci`](https://docs.npmjs.com/cli/commands/npm-ci/)<sup>(英語)</sup>を使用します。

> [!NOTE]
> この方法で依存関係のバージョンを固定することは、「バージョンピニング」と呼ばれることがあります。

つまり、依存関係を更新するには、ビルドシステムがロックファイルを更新するプルリクエストを作成する必要があります。これにより、更新を確認して受け入れるかどうかを判断できます。

#### 更新を確認する

依存関係の更新を確認する際は、その更新を受け入れるかどうかを検討してください。

- リリースの変更履歴を読み、提供される変更内容と、この時点でその更新を受け入れる必要があるかどうかを確認してください。
- 新しい依存関係が追加されていないか確認してください。
- 可能であれば、ソースコードの更新を確認し、説明できない変更や変更履歴と一致しない変更がないか確認してください。
- 更新するまでしばらく待つことを検討してください。サプライチェーン攻撃はセキュリティ研究者によってすぐに発見されることが多く、更新を受け入れる前に悪意あるものだと判明した方が安全です。

### ソフトウェア部品表を維持する

依存関係を詳しく把握するために、それらの詳細なインベントリーを維持できます。これは、ソフトウェア部品表 (SBOM) と呼ばれます。

ロックファイルは実質的に SBOM の一種です。ただし、「SBOM」という用語は通常、依存関係を表現する個別の標準形式を指します。これらの標準は、通常、ロックファイルよりも範囲も詳細度も広くなっています。つまり、次のことができます。

- ロックファイルでは表現されないウェブサービスなどの依存関係を記録する。
- ロックファイルでは表現されない各依存関係の追加情報を記録する。

SBOM を表現する標準形式を使用すると、次のこともできます。

- SBOM をサードパーティーと共有する。
- 法令順守や脆弱性監視などの目的で、SBOM を理解できるツールと統合する。

ソフトウェア部品表を表現する最も一般的な標準は次の 2 つです。

- [CycloneDX](https://cyclonedx.org/): 当初は [OWASP](https://owasp.org/) により開発されました。
- [SPDX](https://spdx.dev/): [Linux Foundation](https://www.linuxfoundation.org/) により保守されています。

これらの標準はどちらも十分に対応されており、プロジェクトの SBOM を表現するためにどちらを使用しても構いません。SPDX は当初、オープンソースソフトウェアライセンスへの準拠を製品が確保できるよう支援することに重点を置いていましたが、セキュリティのユースケースを支援する機能を追加しました。CycloneDX は、当初からサプライチェーンのセキュリティを促進することに重点を置いた、新しくて軽量な標準です。

#### SBOM の構成

> [!NOTE]
> この節では、SBOM 形式の具体的な例として CycloneDX を使用します。
>
> この節では、CycloneDX オブジェクトモデルの最も基本的な部分を簡潔に紹介します。詳細については、CycloneDX の [Authoritative Guide to SBOM](https://cyclonedx.org/guides/OWASP_CycloneDX-Authoritative-Guide-to-SBOM-en.pdf)<sup>(英語)</sup>を参照してください。

CycloneDX では、すべての依存関係が_コンポーネント_または_サービス_のいずれかです。

- コンポーネントには、ソフトウェアフレームワーク、ライブラリー、アプリケーション、設定データなどがありますが、これらに限定されません。
- サービスは、ソフトウェアが呼び出す可能性のある外部 API を表します。例えば、エンドポイント URI を介して呼び出される API です。

製品で直接または間接的に使用されるすべてのコンポーネントとサービスは、SBOM 内のオブジェクトで表現されます。このオブジェクトには、名前、バージョン、作成者、ライセンス、説明、{{glossary("hash_function", "ハッシュ")}}（コンポーネントの場合）、エンドポイント URI（サービスの場合）など、その項目に関する情報が含まれます。

SBOM には、製品の依存関係で特定された脆弱性も記載されます。一覧のそれぞれの項目には、説明、[CWE](https://cwe.mitre.org/index.html)<sup>(英語)</sup>コードの集合、軽減策、アドバイザリーへのリンク、脆弱性の影響を受けるコンポーネントまたはサービスの識別子など、その脆弱性に関する情報が含まれます。

#### SBOM を作成する

[cdxgen](https://cdxgen.github.io/cdxgen/#/) などの独立したツールや、[`npm sbom`](https://docs.npmjs.com/cli/commands/npm-sbom/)<sup>(英語)</sup>などのコマンドを使用して、製品の SBOM を生成できます。SBOM は通常、ビルド工程の一環として生成されますが、ソフトウェアライフサイクルの他の段階で生成することもできます。

#### SBOM を使用する

SBOM を使用すると、サプライチェーン攻撃に対する複数の防御策を実装できます。そのうち最も重要なものは次の 3 つです。

- **脆弱性管理**: SBOM の主な用途の 1 つは、依存関係で特定された脆弱性に対応することです。OWASP の [Dependency-Track](https://dependencytrack.org/)<sup>(英語)</sup> などのサードパーティー製ツールを使用できます。このツールは、[NIST National Vulnerability Database](https://nvd.nist.gov/)<sup>(英語)</sup> や [GitHub Advisories](https://github.com/advisories)<sup>(英語)</sup> などの脆弱性レポートの情報源をスキャンすることで、対応を自動化します。
- **完全性の検証**: SBOM に依存関係のハッシュが含まれている場合、依存関係の提供元の情報が元のリリース形式から変更されていないことを検証できます。
- **サプライヤーリスク管理**: 依存関係のサプライヤーに関する情報を記録することで、SBOM は、もはや信頼できるとみなされないサプライヤーのコンポーネントまたはサービスに依存している状況を把握するのに役立ちます。

## 監視と対応

ウェブサイトをデプロイした後、関連するイベントを記録し、疑わしい可能性のある操作が検出されたときにプロジェクトメンテナーへ警告することで、攻撃の検出と対応を支援できます。

メンテナーは実際の問題について警告を受ける一方で、誤報によって絶えず警告を受けることのないバランスを見つける必要があります。記録すべき特定のイベントや警告を発するイベントの一部は、プロジェクトとその[脅威モデル](/ja/docs/Web/Security/Threat_modeling)によって異なりますが、一般的には次のものが含まれます。

- 入力検証の失敗: ユーザー入力がウェブサイトの想定と異なる場合。入力の種類には、フォーム入力、URL 引数、ファイルアップロードなどがあります。検証失敗には、予想外の値、形式、長さ、引数名を持つ入力が含まれます。存在しない {{htmlelement("select")}} オプションなど、手動では入力できないユーザー入力は特に不審です。

- 認証に関連するイベント:
  - ログイン試行の失敗。特に短時間に繰り返される失敗。
  - 想定外の場所や端末からのログイン。
  - 資格情報の管理イベント: 資格情報の変更、作成、削除。
  - パスワード忘れフローなどの二次フローの実行。

- アクセス制御の失敗: 適切な認可レベルなしにリソースへアクセスしようとする試み。

- [CSP](/ja/docs/Web/HTTP/Guides/CSP)違反: [レポート API](/ja/docs/Web/API/Reporting_API) を使用して報告できます。

また、ユーザーがサイトのセキュリティ上の問題を報告できる手段も提供すべきです。プロジェクトは、リポジトリーのルートディレクトリーにある `SECURITY.md` ファイルを使用して、セキュリティポリシーを示せます。このファイルでは、ユーザーや研究者が脆弱性を報告する方法、報告をどのように扱うか、バグ報奨金プログラムがある場合はその詳細を説明します。

ウェブサイトでは、専用のメールアドレスなど、エンドユーザーがセキュリティ上の問題を報告できる手段も提供できます。

## バックアップの作成

サイト、特にデータの定期的なバックアップは、進行中の攻撃に限定されず、さまざまな問題に対する防御策になります。

- メンテナーのミスや不具合のあるツールにより、データが失われたり破損したりする。
- 書き込み権限を持つ攻撃者による破壊行為。
- 攻撃者が身代金の支払いを受けるまで被害者のデータにアクセスできないようにする（例えば、暗号化する）[ランサムウェア](https://en.wikipedia.org/wiki/Ransomware)<sup>(英語)</sup>攻撃。

バックアップの機密性と完全性も保護すべきです。つまり、バックアップに含まれる機密データに攻撃者がアクセスしたり変更したりできないようにします。
